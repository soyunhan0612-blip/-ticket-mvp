# Step 1: readme-rewrite

## 읽어야 할 파일

먼저 아래 파일들을 읽고 프로젝트의 기획·아키텍처·설계 의도를 파악하라:

- `/CLAUDE.md` — 프로젝트 개요와 CRITICAL 규칙
- `/docs/PRD.md` — 배경·목표·MVP 제외 사항·3대 함정·일정·검증 시나리오
- `/docs/PROGRESS.md` — Day 0~9의 실제 산출물과 결정 근거. **README 진행 표의 원본이다**
- `/docs/ARCHITECTURE.md` — 렌더링 경계, Store 인터페이스, Redis 자료구조, 보안 경계
- `/docs/ADR.md` — ADR-001~005의 결정과 트레이드오프
- `/README.md` — 이번 step의 수정 대상
- `/package.json` — 스크립트 목록
- `/phases/*/index.json` — 각 phase의 step별 `summary`. Day별로 실제 무엇이 끝났는지의 기계 기록

이전 step에서 만들어진 코드와 문서를 꼼꼼히 읽고, 설계 의도를 이해한 뒤 작업하라.

## 배경

이 프로젝트는 채용 지원용 포트폴리오다. README는 심사자가 가장 먼저 그리고 어쩌면 유일하게 읽는 문서다. 현재 README는 Day 0 시점에서 멈춰 있다:

- 진행 상황 표가 `Day 0`만 채워져 있고 `1~9`는 `⏳`로 뭉뚱그려져 있다
- 심사자용 계정이 `TBA`로 남아 있다
- `docs/PRD.md`의 Day 10 항목이 요구한 세 가지 — **데모 GIF**, **성능 before/after 표**, **"알고도 제외한 것"** — 이 전부 없다

`docs/PRD.md`의 MVP 제외 사항 절은 이렇게 적고 있다: *"모르고 안 한 것과 알고 안 한 것은 다르게 읽힌다."* README가 이 구분을 보여주지 못하면 의도적 스코프 결정이 그냥 누락으로 읽힌다.

## 작업

`README.md`만 수정한다. 다른 파일은 만들지도 고치지도 않는다.

### 포함할 내용

**1. 프로젝트 소개** — 무엇을 만들었는지 몇 문장. `docs/PRD.md`의 배경·목표 절이 원본이다. 좌석 선택 화면이 시각적·기술적 시그니처라는 점, 서버 hold가 있어서 "동시에 두 명이 같은 좌석을 고르면?"에 답할 수 있다는 점이 핵심 주장이다.

**2. 데모** — 데모 GIF를 넣을 자리를 만든다. 이미지는 `docs/assets/` 아래를 가리키되 **파일이 아직 없으므로 자리만 마련하고, 없는 파일을 있는 것처럼 쓰지 마라.** 어떤 장면을 담을 GIF인지(탭 2개에서 같은 회차를 열고 한쪽이 좌석을 잡으면 반대편이 다음 폴링 주기에 회색으로 바뀌는 장면) 캡션으로 적어라.

**3. 기술 스택과 아키텍처 요약** — Next.js 15 App Router(RSC), TypeScript strict, Tailwind, TanStack Query, Jotai, vitest, Upstash Redis. 각 선택의 근거는 길게 쓰지 말고 `docs/ADR.md`로 연결한다. 특히 **TanStack Query와 Jotai를 쓴 이유가 서버 hold 때문에 실제로 생겼다**는 점은 README에서 한 번 짚어야 한다 — 스택 흉내가 아니라는 주장의 핵심이다.

**4. 진행 상황 표** — Day 0~9를 실제 산출물로 채운다. `docs/PROGRESS.md`의 각 Day 섹션과 `phases/*/index.json`의 `summary`가 원본이다. 없는 것을 완료로 적지 마라.

**5. 성능 before/after 표** — 골격만 만들고 수치는 `TBD`로 둔다.

| 측정 | Day 3 (before) | Day 4 (after) |
|---|---|---|
| 좌석 1회 클릭 시 리렌더 컴포넌트 수 | TBD | TBD |
| 초기 마운트 시간 | TBD | TBD |

표 아래에 **정직 조건**을 반드시 함께 적는다: `atomFamily` + `React.memo`가 개선하는 것은 **업데이트 시 리렌더 수**이지 **초기 마운트 비용**이 아니다. 2000개 SVG 노드 생성은 구조적으로 남는다. `docs/ADR.md`의 ADR-002가 이 조건을 명시하고 있으며, 과장하면 면접에서 그 자리에서 깨진다고 못박고 있다.

**6. "알고도 제외한 것"** — `docs/PRD.md`의 MVP 제외 사항 6개를 각각 **제외 이유와 함께** 적는다:
- 좌석 키보드 내비게이션 / 스크린리더
- E2E (Playwright)
- 모바일 터치 제스처 정밀 튜닝
- 실사용자 인증·결제
- CSRF 토큰
- 좌석 배치 에디터

`docs/PRD.md`의 「3대 함정」(좌석 배치 에디터 / 차트 라이브러리 / SSE·WebSocket)도 이 절에 녹이면 판단의 일관성이 드러난다. **CSRF 토큰은 `sameSite: 'lax'` 쿠키로 대체했으며 실서비스라면 별도 토큰이 필요하다는 점을 명시하라** — `docs/PRD.md`와 `docs/ADR.md` ADR-005가 README에 적으라고 요구한 항목이다.

**7. 로컬 실행** — 기존 「요구사항」·「설치 & 실행」·「스크립트」 절은 유효하므로 유지하거나 다듬는 선에서 둔다.

**8. 심사자용 계정** — `/admin`, `/seller/new`가 Basic Auth 뒤에 있다는 안내와, 계정을 적을 자리를 만든다. 값은 `<BASIC_AUTH_USER 값>` / `<BASIC_AUTH_PASS 값>` 형태의 자리표시자로 둔다.

**9. 데이터 영속성 / 배포** — 기존 절이 이미 정확하므로 유지한다. 배포 URL도 그대로 둔다.

**10. 문서 링크** — 기존 절 유지.

### 원칙

- README는 심사자가 순서대로 읽는 문서다. 위 번호는 권장 순서일 뿐 절대적이지 않으니, 읽는 흐름이 더 나은 배치가 있으면 재량으로 조정하라
- 문서 톤은 `docs/PROGRESS.md`와 맞춘다. 과장된 형용사와 마케팅 문구를 쓰지 마라

## Acceptance Criteria

```bash
npm run lint
npm test
```

문서만 바뀌므로 테스트 수는 그대로여야 한다.

## 검증 절차

1. 위 AC 커맨드를 실행한다.
2. README를 처음 읽는 사람의 관점에서 확인한다:
   - 무엇을 만들었는지, 왜 그 스택을 썼는지가 드러나는가?
   - 무엇을 **알고도** 제외했는지가 드러나는가?
   - 완료되지 않은 것을 완료로 적지 않았는가?
3. 아키텍처 체크리스트를 확인한다:
   - CLAUDE.md CRITICAL 규칙을 위반하지 않았는가?
4. 결과에 따라 `phases/10-release/index.json`의 해당 step을 업데이트한다:
   - 성공 → `"status": "completed"`, `"summary": "산출물 한 줄 요약"`
   - 수정 3회 시도 후에도 실패 → `"status": "error"`, `"error_message": "구체적 에러 내용"`
   - 사용자 개입 필요 → `"status": "blocked"`, `"blocked_reason": "구체적 사유"` 후 즉시 중단

## 금지사항

- 성능 수치를 추정해서 적지 마라. 반드시 `TBD`로 둔다. 이유: 측정은 React DevTools Profiler로 사람이 브라우저에서 해야 하며, step2가 실측값으로 채운다. 추정치를 적으면 이 프로젝트의 유일한 정량 증거가 거짓이 된다
- `.env.local`에서 `BASIC_AUTH_USER`/`BASIC_AUTH_PASS`의 실제 값을 읽어 README에 쓰지 마라. 이유: README는 공개 저장소에 커밋되며, 자동화가 비밀을 저장소로 밀어넣는 경로를 만들어서는 안 된다. 값은 사람이 확정한 뒤 직접 채운다
- 존재하지 않는 이미지 파일을 `![](...)`로 참조해 깨진 링크를 만들지 마라. 이유: 심사자가 가장 먼저 보는 문서에서 깨진 이미지는 프로젝트 전체의 신뢰도를 깎는다. 자리와 캡션만 마련하고 파일이 없다는 사실을 숨기지 마라
- `README.md` 이외의 파일을 수정하지 마라. 이유: `docs/` 최종화는 step2의 범위이며, 두 step이 같은 파일을 건드리면 변경 이력이 섞인다
- 소스 코드를 수정하지 마라. 이유: 이 step은 문서 작업이다. 코드 문제를 발견하면 고치지 말고 `summary`에 기록하라
- 배포 URL을 추측해서 바꾸지 마라. 이유: 현재 README에 적힌 URL이 실제 프로덕션이다
- 기존 테스트를 깨뜨리지 마라
