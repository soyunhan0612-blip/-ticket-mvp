# Step 2: metrics-docs

## 읽어야 할 파일

먼저 아래 파일들을 읽고 프로젝트의 기획·아키텍처·설계 의도를 파악하라:

- `/CLAUDE.md` — CRITICAL 규칙
- `/docs/PRD.md` — Day 10 항목과 검증 시나리오
- `/docs/PROGRESS.md` — Day 3·Day 4·Day 9 섹션의 측정 플레이스홀더가 여기 있다
- `/docs/ADR.md` — ADR-002(before/after 측정 정직 조건), ADR-004(폴링 1회당 커맨드)
- `/docs/ARCHITECTURE.md` — 좌석 성능 전략, Redis 자료구조
- `/README.md` — 성능 표의 `TBD` 자리표시자가 여기 있다
- `/docs/assets/` — 측정 스크린샷이 있다면 여기 있다

이전 step에서 만들어진 문서를 꼼꼼히 읽고, 설계 의도를 이해한 뒤 작업하라.

## 사전 조건 — 측정값이 없으면 즉시 중단

이 step은 **사람이 브라우저와 외부 콘솔에서 측정한 값을 문서에 반영하는 작업**이다. 실행 세션은 React DevTools Profiler를 열 수도, Upstash 콘솔에 로그인할 수도 없다.

작업을 시작하기 전에 아래 값이 주어졌는지 확인하라. 프롬프트 본문, `docs/assets/`의 스크린샷, 또는 문서에 이미 기록된 값 중 어디서든 확인할 수 있으면 된다.

**필요한 측정값**
1. Day 3(순진한 구현) — 좌석 1회 클릭 시 리렌더 컴포넌트 수, 초기 마운트 시간(ms)
2. Day 4(`atomFamily` + `React.memo` 적용 후) — 같은 두 수치
3. `ZoomPanSvg` 도입 이후 좌석 클릭당 리렌더 컴포넌트 수 (Day 9에서 좌석맵 구조가 바뀌어 재측정이 필요하다고 기록돼 있다)
4. Upstash 콘솔 기준 스냅샷 폴링 1회의 실제 커맨드 수 — 특히 Lua `EVAL`이 몇 커맨드로 과금되는지

**위 값이 하나도 주어지지 않았다면 아무 파일도 수정하지 말고 즉시 `phases/10-release/index.json`의 이 step을 `"status": "blocked"`로 표시하고 중단하라.** `blocked_reason`에 어떤 값이 없는지 구체적으로 적어라.

일부만 주어졌다면 **주어진 값만 반영하고**, 나머지 플레이스홀더는 그대로 둔 채 `summary`에 무엇이 아직 비어 있는지 명시하라. 없는 값을 추정해서 채우지 마라.

## 배경

이 프로젝트의 성능 서사는 "2000석을 순진하게 짜면 클릭 하나에 2000개가 리렌더된다 → `atomFamily`로 좌석 단위 구독을 만들어 1~2개로 낮췄다"이다. `docs/ADR.md`의 ADR-002가 이 서사를 프로젝트의 **정량 증거**로 규정했고, Day 3의 순진한 구현을 일부러 별도 커밋으로 남긴 이유도 이것이다.

그런데 정작 수치가 비어 있다. `docs/PROGRESS.md`의 Day 3 「before 측정」과 Day 4 「after 측정」 절이 `**_ ms` 형태의 플레이스홀더 상태이며, Day 9 섹션은 `ZoomPanSvg` 도입으로 좌석맵 구조가 바뀌었으니 재측정이 필요하다고 기록해 두었다. 증거가 없으면 서사 전체가 주장으로만 남는다.

`docs/ADR.md`의 ADR-004도 폴링 1회당 커맨드 수를 **코드를 읽어 센 값**이라고 명시하면서 "Upstash 콘솔 실측은 아직 못 했다"고 적고 있다.

## 작업

### 1. `docs/PROGRESS.md`

- Day 3 「before 측정 (React DevTools Profiler)」 절의 플레이스홀더를 실측값으로 교체한다
- Day 4 「after 측정 (React DevTools Profiler)」 절도 같게 처리한다. Day 3 대비 비교 표기를 유지한다
- Day 9 「성능 측정 후속」 절 — `ZoomPanSvg` 도입 이후 재측정값을 반영한다. 재측정 결과가 Day 4와 다르면 **왜 달라졌는지 추측하지 말고 수치만 정직하게 병기하라**
- 스크린샷 파일이 `docs/assets/`에 실제로 존재할 때만 경로를 참조한다

### 2. `docs/ADR.md`

- ADR-004의 「Upstash 콘솔 실측은 아직 못 했다」 문단을 실측 결과로 교체한다
- 실측값이 코드로 센 값(폴링 1회 = `HGETALL` + `GET` = 2커맨드)과 **다르면 차이를 그대로 적고, 원래 추정이 틀렸다는 사실을 지우지 마라.** ADR은 결정과 그 근거의 이력이지 결과만 남기는 문서가 아니다
- 실측 결과가 Free 한도 계산(월 50만 커맨드 대비 비율)에 영향을 주면 해당 표도 갱신한다

### 3. `README.md`

- step1에서 만든 성능 before/after 표의 `TBD`를 `docs/PROGRESS.md`와 **동일한 값**으로 채운다. 두 문서의 숫자가 어긋나면 안 된다
- ADR-002가 요구한 정직 조건(개선되는 것은 업데이트 시 리렌더 수이지 초기 마운트 비용이 아니다)이 표 근처에 남아 있는지 확인한다

### 4. `docs/PRD.md` · `docs/ARCHITECTURE.md` 최종 검토

읽으면서 **구현과 실제로 어긋난 서술만** 교정한다. 문장을 다듬기 위한 편집은 하지 마라. 어긋난 곳을 발견했지만 수정 범위가 크면 고치지 말고 `summary`에 기록하라.

## 검증 절차

1. 위 AC 커맨드를 실행한다.
2. 문서 간 일관성을 확인한다:
   - `README.md`와 `docs/PROGRESS.md`의 성능 수치가 동일한가?
   - 추정한 숫자를 실측인 것처럼 적지 않았는가?
   - 아직 측정하지 못한 항목이 "측정 대기"로 남아 있는가, 아니면 조용히 사라졌는가? (사라지면 안 된다)
3. 아키텍처 체크리스트를 확인한다:
   - CLAUDE.md CRITICAL 규칙을 위반하지 않았는가?
4. 결과에 따라 `phases/10-release/index.json`의 해당 step을 업데이트한다:
   - 성공 → `"status": "completed"`, `"summary": "반영한 수치와 아직 비어 있는 항목"`
   - 수정 3회 시도 후에도 실패 → `"status": "error"`, `"error_message": "구체적 에러 내용"`
   - 측정값 부재 등 사용자 개입 필요 → `"status": "blocked"`, `"blocked_reason": "어떤 측정값이 없는지"` 후 즉시 중단

## 금지사항

- 측정값을 추정하거나 그럴듯한 숫자로 채우지 마라. 이유: 이 수치가 프로젝트의 유일한 정량 증거다. `docs/ADR.md` ADR-002가 "과장하면 면접에서 그 자리에서 깨진다"고 명시했다. 값이 없으면 `blocked`가 정답이다
- 개발 서버를 띄워 성능을 측정하려 시도하지 마라. 이유: React DevTools Profiler는 브라우저 확장이며 실행 세션이 접근할 수 없다. 다른 방식으로 잰 숫자를 Profiler 측정값 자리에 넣으면 측정 조건이 달라져 비교가 무의미해진다
- Upstash 콘솔 수치를 코드에서 유추해 실측으로 기록하지 마라. 이유: ADR-004가 코드로 센 값과 콘솔 과금 단위를 구분해 두었고, 그 구분을 지우는 것이 이 항목이 남아 있는 이유를 없앤다
- 원래 추정이 틀렸다는 기록을 삭제하지 마라. 이유: ADR은 결정 이력 문서다. 틀린 판단이 교정된 과정 자체가 읽을 가치가 있다
- 소스 코드를 수정하지 마라. 이유: 이 step은 문서 작업이다. 측정 결과 성능 문제가 보이면 고치지 말고 `summary`에 기록하라
- `docs/assets/`에 없는 스크린샷을 참조하지 마라. 이유: 깨진 이미지 링크가 생긴다
- 기존 테스트를 깨뜨리지 마라
